The benchmark's logical graph is constant: typed financial entities connected by directed, typed, property-bearing relationships. What changes by engine is whether a relationship is a native graph edge, a row in an edge table, or an adjacency record addressed by a key. That physical choice determines which identifiers, indexes, partition keys, and denormalized copies the schema must provide.

Neo4j

Native property graph

Sample stored relations

Cypher-style property-graph records. Repeated transfer events are separate relationship records; these examples show graph-level data, not Neo4j's internal byte layout.

(:Account {id: 10001})-[:transfer {createTime: 1710000000000, amount: 5000, order: 2}]->(:Account {id: 10002})
(:Person {id: 501})-[:own {createTime: 1710000000000}]->(:Account {id: 10001})
(:Account {id: 10001})-[:repay {createTime: 1710000005000, amount: 125}]->(:Loan {id: 9001})

Logical relations & traversal

Each entity is a labeled node; each relation is a directed, typed edge with its own properties. Cypher expresses a k-hop walk as -[:transfer* k]->. The repository's Cypher path returns up to ten endpoints; DirectedTrail instead matches a fixed-depth path to a target. The Cypher form does not explicitly forbid revisiting nodes.

Physical model

Identity is represented by each node label plus id. The schema creates uniqueness constraints for the five node labels, property indexes for common node filters, and relationship-property indexes for timestamps, amounts, and order fields. Relationships remain native graph records rather than join rows.

Schema changes to consider

  • Keep stable, unique node IDs and the existing label-specific uniqueness constraints.
  • Choose relationship identity semantics deliberately: transfer events may repeat, while bulk reloads should not accidentally duplicate the same event. Add an event ID or a deterministic idempotency key if ingestion retries require it.
  • Retain indexes only for measured start-node lookups and selective filters; validate relationship-property indexes against actual predicates because they do not replace adjacency expansion.
  • Use label/type and property constraints to validate required fields and temporal/amount types at ingestion boundaries.

Implementation note

The direct exporter uses MERGE for vertices, then CREATE for relationships. Thus vertex loads are idempotent by label/id, while repeated edge loads can create duplicates unless the ingestion process is controlled or edge identity is added.

value: [{"ownerId":501,"ownerType":"Person","accountId":10001,"createTime":1710000000000}]

key: adj:out:Loan:9001:deposit
value: [{"loanId":9001,"accountId":10001,"createTime":1710000005000,"amount":200}]

Logical relations & traversal

Relations are JSON edge records grouped by source entity, source ID, and edge type. A traversal is application code: MultiGet expands a frontier with a configured beam width; DFS follows the first outgoing edge at each hop. The cache does not parse or enforce graph semantics.

Physical model

Vertices use keys such as v:Account:10001. Outgoing edges use adj:out:Account:10001:transfer with an array of edge records, including their destination and event properties. These values are volatile cache entries, not a durable source of truth.

Schema changes to consider

  • Define canonical key encoding, edge field names, and type conversion once; the current exporter emits outgoing lists only even though the design document also describes incoming lists.
  • Add reverse adjacency keys only if reverse traversals are required, and ensure writes update both directions consistently.
  • Plan for cache expiry/eviction, rebuild from durable storage, and invalidation on updates or deletes.
  • Bound adjacency value sizes: split high-degree lists into pages/chunks and consider hot-key distribution for popular accounts.
  • Preserve event IDs and timestamps if repeated transfer records, temporal filtering, or deduplication matter.

Implementation note

The exporter groups each edge batch by source and writes one JSON array per source/type key. The benchmark's BFS issues one multi-get per hop; DFS performs sequential gets, so depth adds round trips to DFS while breadth adds frontier size to BFS.

AWS Neptune

Managed property graph

Sample stored relations

Gremlin API-level examples of native Neptune vertices and edges. Neptune manages the underlying storage records; these are not bulk-loader rows or a claim about its internal format.

g.V().has('Account', 'id', 10001).addE('transfer')
  .to(g.V().has('Account', 'id', 10002))
  .property('createTime', 1710000000000).property('amount', 5000).property('order', 2)

g.V().has('Person', 'id', 501).addE('own')
  .to(g.V().has('Account', 'id', 10001)).property('createTime', 1710000000000)

g.V().has('Account', 'id', 10001).addE('repay')
  .to(g.V().has('Loan', 'id', 9001))
  .property('createTime', 1710000005000).property('amount', 125)

Logical relations & traversal

Vertices and edges have labels; edges are directed and may carry properties. Gremlin expresses the benchmark traversal as g.V().has('Account','id',id).repeat(out('transfer')).times(k). The adapter also constructs openCypher variable-length paths and SPARQL property paths, although only the Gremlin route is represented in this saved run.

Production query model

At query time, Neptune stores and traverses native labeled vertices and property-bearing edges through the managed graph engine; the underlying storage layout is service-managed. This repository writes Neptune bulk-loader CSV with ~id, ~label, ~from, and ~to fields as an ingestion format, not as the runtime model.

Schema changes to consider

  • Keep vertex IDs globally unambiguous across labels; the exporter prefixes IDs with entity type.
  • Use stable unique edge IDs, especially for repeated transfers and repeatable bulk loads; validate the current generated ID scheme against the source event key.
  • Keep labels and property names/types consistent across loader CSV and query text; validate endpoint references before loading.
  • Choose property cardinality and indexing behavior based on deployed Neptune engine/version and actual predicates; don't assume relational-style user-created indexes from this sample.
  • For production bulk loads, define a durable object-store staging process and load/retry validation; the local exporter currently writes CSV files.

Implementation note

The schema file documents labels and a sample Gremlin traversal rather than executable DDL. Its sample uses simplePath(), while the benchmark adapter's Gremlin query does not, so cycle avoidance is not identical between the example and measured path.

Repay(accountId, loanId, createTime, amount)
  (10001, 9001, 1710000005000, 125)      -- graph edge label: repay

The current primary keys are source-first. Some association tables omit event time from their key, so they cannot retain repeated same-pair events even though the timestamp is a column.

Logical relations & traversal

The property graph is declared over relational node and edge tables. Each edge-table row maps source and destination key columns to graph endpoints and receives a graph label. GQL uses a variable-length graph pattern. The SQL comparison bypasses graph traversal and joins the Transfer table repeatedly, in batches of at most five hops.

Physical model

Entity tables use id primary keys. Event edges such as Transfer use composite keys beginning with the source ID, then destination and timestamp. The graph definition maps edge tables to labels and endpoint node tables. The current DDL has no secondary indexes.

Schema changes to consider

  • Choose primary-key prefix order from dominant access direction. Source-first keys suit outgoing traversals; add destination-first secondary indexes for reverse traversal and account for their write/storage cost.
  • Evaluate INTERLEAVE IN PARENT for source-owned edge rows when colocating a source entity and its outgoing edges benefits the workload; weigh reverse traversal and write concentration before choosing it.
  • Include a stable event discriminator or timestamp in the key wherever multiple edges between the same endpoints must coexist. The current PersonOwnAccount, CompanyOwnAccount, PersonApplyLoan, CompanyApplyLoan, and WorkIn primary keys omit timestamp and therefore cannot store multiple rows for the same endpoint pair.
  • Add secondary indexes for selective filters only after query-plan review; keep graph endpoint key columns aligned with the property-graph definition.

Implementation note

The current graph definition maps ownership and application relations from different source types via separate tables that share graph labels. The benchmark's SQL variant only traverses transfers, so its SQL/GQL comparison does not exercise the full set of relation types.

Logical relations & traversal

The Gremlin API exposes property-graph vertices and labeled edges. The adapter starts at an Account selected by id and follows outgoing transfer edges for exactly k steps. In a partitioned graph, where related items live determines whether each step stays local or incurs cross-partition work.

Physical model

The graph container is configured with partition-key path /pk; Terraform configures provisioned throughput. The schema note says all properties are indexed, but this repo has no Cosmos data exporter or executable graph schema creation beyond the Terraform graph/container setup and those comments.

Schema changes to consider

  • Define what pk means and ensure every graph element is written with it. Align partitioning with the common start-vertex and traversal access pattern.
  • Assess whether related vertices and edges can be co-located without creating hot partitions for high-degree accounts; benchmark realistic skew and cross-partition traversal.
  • Make partition-key value available in point lookups where possible; label/id alone may require broader lookup work if it doesn't identify a partition.
  • Review indexing policy against actual property filters and write volume rather than relying on the schema note's blanket all-properties statement.
  • Make throughput mode and RU budget explicit for traversal depth and fan-out; exact hop count alone does not predict RU use.

Implementation note

The Cosmos SQL alias is not currently a working path: the adapter's SQL mode does not connect, while the Gremlin mode is the implemented traversal. The Gremlin schema file is only a comment stub, so partition-key and indexing guidance should be treated as design intent, not proof that generated graph items currently contain pk.

Database modeling types: strengths and tradeoffs

Compare these designs as long-running services answering concurrent, bounded multi-hop reads over skewed financial graphs. The critical differences are query execution, degree/fan-out behavior, partition or key hotspots, and the capacity unit that eventually throttles or saturates.

Neo4j

Graph-native model

Strengths

Database-side path expansion avoids an application round trip for every hop; native adjacency and typed edge properties fit variable-length queries. Identity indexes locate the starting vertex.

Tradeoffs

Runtime grows with visited edges and branching factor; large unbounded path patterns can consume CPU and memory. Use selective starts, depth/frontier bounds, and query plans for production traffic.

Capacity watch

Size memory/page cache and compute for the hot working set and concurrent traversal load. A supernode remains expensive even in a highly available cluster; availability replicas do not make fan-out free. No universal graph-size cap is assumed here: practical capacity depends on deployment topology and workload.

Memcached

Application-managed key-value graph cache, not a graph database

Strengths

Key lookups and batched frontier fetches can serve bounded, read-heavy hops with low per-lookup overhead. The application can pre-shape adjacency for a known query mix.

Tradeoffs

Every BFS layer adds client coordination and network work; DFS adds serial round trips. The client must maintain edge integrity, reverse access, freshness, and fallback behavior after cache misses.

Capacity watch

Total memory is finite across shards, but a single hot adjacency key is owned by one shard and cannot be spread by adding nodes. Large adjacency values approach the configured item-size limit; chunk or page them, watch hot-key QPS, and account for eviction.

AWS Neptune

Managed graph-native model

Strengths

Gremlin traversals run in the graph service over native edge adjacency, avoiding application-managed hop-by-hop fetching. Managed replicas and supported query interfaces can fit graph-serving systems.

Tradeoffs

Traversal plans and resource behavior are service/version specific, and broad expansion can dominate latency. Managed storage limits low-level control; validate Gremlin semantics, concurrency, and observed throttling on the deployed engine.

Capacity watch

Compute is bounded by the selected instance classes and service quotas; reader capacity can help read throughput but does not eliminate one query's high-degree expansion. Monitor CPU/memory pressure and query latency, and bound depth/fan-out.

Google Cloud Spanner Graph

Relational physical model with graph projection

Strengths

GQL evaluates graph patterns over a relationally defined schema; provisioned nodes support predictable concurrent service capacity. Source-first edge keys or source-parent interleaving can keep common outgoing edges near their owner.

Tradeoffs

GQL and hand-built SQL joins are distinct query plans and should not be treated as the same traversal engine. Key order, interleaving, and indexes trade outgoing locality against reverse access and write distribution.

Capacity watch

Adding nodes increases provisioned capacity, but uneven key ranges and high-traffic source IDs can still hotspot splits. Interleaving may concentrate a parent's edge rows; monitor split/transaction latency and design reverse indexes only for measured paths.

Azure Cosmos DB Gremlin API

Managed graph with partition-keyed storage

Strengths

Gremlin keeps traversal expressed as graph operations while provisioned request units can be adjusted for a production workload. The service manages partitioned graph storage.

Tradeoffs

Cross-partition traversal adds request work and latency; a partition key optimized for one traversal may distribute other access patterns poorly. RU cost rises with depth, fan-out, and returned data.

Capacity watch

Account-wide RU/s is not a guarantee that every partition can serve that rate: a hot logical partition can throttle while other capacity is idle. High-degree accounts can create hot partitions; partition throughput and storage ceilings are service/version-specific, so validate current quotas and skewed load.

How to read this comparison: Neo4j and Neptune place graph semantics in the database; Spanner stores relational rows and projects them as a graph; Cosmos exposes a graph API over partitioned managed storage; Memcached stores application-encoded adjacency and has no native graph semantics. Benchmark results therefore compare these implemented access paths, not equivalent levels of database functionality.
